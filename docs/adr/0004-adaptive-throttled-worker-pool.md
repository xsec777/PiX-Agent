# ADR 0004 — 自适应滑动窗口并发池与防封流控机制 (Adaptive Throttled Worker Pool)

## 状态
已采纳（2026-11-04，设计决策）

**v2.9.1 实现状态：未实现的目标架构。** 现有传感与节奏逻辑不等同于本文的 WorkerPool、站点互斥和自适应并发窗口；这些调度机制尚未实现。下文保留目标设计，安全与效率收益不属于本版本保证。文中场景与示例均为虚构，不代表实测。

## 背景
在黑盒自动化渗透测试中，发包并发度是平衡测试效率与安全合规的核心矛盾点：若并发过高，极易触发目标反向代理（如 Cloudflare、阿里云盾、深信服 WAF）的频控黑名单（HTTP 429 / 验证码挑战），甚至导致目标 Web 容器资源耗尽崩溃（严重触犯无害化红线）；若全量单线程串行探测，面对 50+ 接口的复杂系统，总测试时长又难以接受。盲目追求高并发是初级扫描器的典型缺陷，工业级攻防智能体必须具备自适应感知现场反馈并动态调节并发节奏的机智。

## 决策
我们决定采用 **自适应滑动窗口并发池 + 站点互斥 + 阻断自适应降级机制 (Adaptive Throttled Worker Pool)**：
1. **轻量受控并发窗口 (Concurrency Window)**：
   - 默认并发上限设为 `maxConcurrency = 2 ~ 3`；
   - 绝不采用无上限或静态死板的数十并发。
2. **站点级互斥锁 (Host Mutex)**：
   - 依据目标端点的域名 / 目标 IP 实施站点互斥锁定；
   - **核心纪律**：对同一个目标站点，同一时间绝对只允许 1 个 Worker 发送网络探针，彻底杜绝单站点瞬时并发过载；不同独立站点/子域之间允许安全并发。
3. **阻断自适应瞬间降级 (Adaptive Throttle)**：
   - 联动 `sensor.ts` 与 `pacing.ts` 传感器：一旦任意一个 Worker 遭遇 HTTP 429（限流）、云 WAF 拦截（403）、人机验证挑战或连接超时，系统立即触发自适应熔断：
     ① 全局并发窗口瞬间收缩至 `1`（全面转入保守单并发测试）；
     ② 全局注入 3~5 秒冷却休眠；
     ③ 待系统连续累计 10 次正常响应且无防御阻断后，并发窗口再平滑递增恢复至基线（2~3）。

## 后果与权衡
- **积极影响**：
  - 严格遵守授权渗透无害化红线，将触发 WAF 封禁和业务容器宕机的风险降至接近 0；
  - 站点互斥 + 跨站并发使多目标攻击面扫描效率相较传统纯串行提升 2~3 倍；
  - 动态呼吸式的并发调节在可视化大屏上极具实战专业度与工程可解释性。
- **代价与约束**：
  - 需要在 `WorkerPool` 中维护站点互斥锁表与窗口滑动控制器；
  - 调度队列推导时需优先挑选不同站点的待测端点以最大化利用并发槽位。
