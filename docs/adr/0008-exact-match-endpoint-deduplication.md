# ADR 0008 — 资产原始现场保全与完全匹配去重 (Exact-Match Endpoint Deduplication)

## 状态
已采纳（2026-11-04，设计决策）

**v2.9.1 实现状态：部分实现。** `state.ts` 的 `recordEndpoint` 按大写后的 HTTP method 与 `url.trim()` 后的完整 URL 精确去重，不泛化路径。但 `sniffer.ts` 会过滤静态资源、补全相对 URL，且单次提取最多保留 40 个不同端点，不能等同于全量原始资产保全。下文保留目标设计，“100% 保真/零误杀”等表述不是本版本能力保证。文中路径与场景均为虚构示例，不代表实测。

## 背景
在信息搜集阶段，爬虫（`katana`）、JS 逆向（`URLFinder`、`rg_cli.py`）与目录爆破工具往往输出海量包含动态数字或参数的 URL。一种常见的做法是采用启发式正则代码将 `/user/101`、`/user/102` 自动归类为 `/user/{id}`。然而在真实的复杂 Web 业务中，这种代码层的主观归纳存在致命的**误杀风险**：许多老旧或异构系统采用数字区分完全不同的业务接口（例如 `/step/1` 是只读查看，`/step/2` 是提交审批；或者数字后挂载完全不同的权限校验逻辑）。一旦代码层粗暴合并，真正的脆弱攻击面将被代码直接吞噬，造成严重漏报。

## 决策
我们决定采用 **资产原始现场保全与完全匹配去重原则 (Raw Asset Preservation & Exact-Match Only)**：
1. **完全匹配物理去重**：
   - 在 `sniffer.ts` 与 `recordEndpoint` 链路中，**代码层绝对不做任何破坏性的 RESTful 路由参数泛化或有损合并**；
   - 仅当两个端点的 `HTTP Method` 与 `URL 完整字符串（含 Query 参数）` 100% 逐字完全相同时，才执行幂等去重；
2. **现场第一手证据绝对忠实**：
   - 扫描器、爬虫回显的原生字符完整保留，确保入账台账与原始网络流量 100% 对应；
3. **语义聚类交由模型端权衡**：
   - 面对大量同构 ID 参数（如 `/user/1`、`/user/2`），由主控 Planner 或 Worker 在阅读上下文时自行实施语义理解与抽样优先级调度，底层状态机绝不越俎代庖裁剪现场资产。

## 后果与权衡
- **积极影响**：
  - 零误杀率：绝对不会因为代码层正则缺陷误吞任何特殊命名的关键业务接口；
  - 证据链完全保真：台账数据与原始发包/扫描日志完全对齐，具备无可争辩的复现可信度。
- **代价与约束**：
  - 端点台账中可能会出现数十条仅 ID 不同的同构接口，略微增加台账行数；
  - 需要在提示词与调度策略中提醒模型在派发 Worker 时注意同族接口的代表性测试，避免连续多次无意义的同参重复发包。
